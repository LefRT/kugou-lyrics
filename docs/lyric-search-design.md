# 酷狗歌词语义搜索与场景歌单设计稿

用户可以用自己的话找一段歌词，也可以在「放学路上」这类常回来的场景里，让系统挑一批今天还想听的歌。搜索结果先给原句，再解释它与请求的关系，点一下就从这几句开始听。场景歌单继承同样的歌词匹配能力，并用实际播放历史保证接下来几次有新鲜感。

## 一次完整的使用

用户输入「回老家却像个客人，想听有人唱出这种感觉，别劝我往前看」。搜索先找与归乡直接相关的歌，再找外在环境熟悉、自己却失去归属感的歌。后一类结果可以标出「相似的是感觉」，让用户决定是否试听。某首歌的主歌说中了，尾声却明确劝人向前走，系统只在适合片段的结果里呈现它。

用户下次打开保存的「放学路上」，可以沿用上次的听歌偏好，也可以补一句「今天想安静听点东西」。这次的请求决定选什么，场景的播放历史决定哪些作品近期先避开。「放学路上」本身只说明用户在哪里听。有需要时，用户可以明确要求歌词也写放学或回家。

## 歌词档案

每首有歌词的歌生成一篇约 800 字的中文赏析，以及供搜索使用的结构化档案。模型一次通读完整歌词，先整理有证据的解读，再写赏析。档案同时保留整首、段落和具体解读三个层级。

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| 原文 | 歌曲 ID、歌词版本、行 ID、原文和已有时间轴 | 回查证据、定位试听、同步高亮 |
| 整首 | 字面处境、说话者与对象、核心矛盾、推进和结尾姿态 | 识别全曲落点，审核整首推荐 |
| 段落 | 有序歌词行、段落角色、白话释义 | 捕捉主歌、桥段、尾声和同一副歌在不同位置的作用 |
| 解读 | 一条具体读法、处境和内心拉扯、叙述者态度、意象、可回应的需求、易混需求、证据和限制 | 作为主要的语义检索单元，可独立核查 |
| 赏析 | 通读后的白话、意象、写法、转折与开放读法 | 给用户阅读，也用作对照评测的检索基线 |

一段虚构歌词「门牌还是从前那个／他们问我这趟住几晚」可以解释为「地点没变，自己却从这里的人变成了访客」。两句原文分别支撑熟悉感和访客感。人物关系仍可能有多种读法。模型写的「适合回应什么需求」表示歌词可以提供怎样的表达，音乐的速度、响度和听感需要音频、现成曲风数据或人工标注支持。

播放层沿用库内 `song_id` 和现有时间轴。KRC 有逐字数据时逐字高亮，LRC 使用行级时间。只有文本的档案可以被搜到和阅读，定点试听以有效时间锚点与音源为条件。分析、源歌词和时间轴都有版本，更新时按版本检查引用，避免一份旧解读跳到新版歌词的错误位置。同作品的录音各自保留时间轴。

离线处理的输入、字段和交付格式以 [歌词档案批处理提示词](lyric-archive-batch-prompt.md) 为准。当前库只读清点出 3,240 条歌曲记录，其中 3,198 条含非空、非制作信息的歌词行。这是一次快照，正式批次按当时实际来源清点。

## 检索和推荐流程

1. **理解这次请求。** 保留原话，分别抽取字面处境、内心矛盾、听歌目的、明确限制和普通偏好。对象、关系、动机缺失时保留未知。对「伤心」这样的宽泛请求，用「陪我难过」「替我说出来」「想换个心情」等方向各找少量代表。用户选了一个方向，再收窄结果。
2. **从不同角度找候选。** 原文与意象用于匹配具体画面。白话与情感结构用于匹配相似处境、相同拉扯或相似姿态。可回应的需求与自然语言示例用于匹配用户希望歌曲做什么。按各路名次合并，并保留每路高质量候选的入围名额。易混需求供精排判别边界。全曲和段落都能入围。可从小曲库实测开始，每次合并约 60 至 100 首，再从中挑二三十首供模型核对。
3. **按证据判定贴合程度。** 精排只看入围解读、证据句、附近上下文、结尾和本次需求。输出命中的需求、证据行、范围和可能的冲突。可按「贴切」「合格的类比」「仅有共同主题」「冲突或证据不足」分档。较强的明示要求以通过核对为准。整首与片段分开判定，同一版本的歌只占一个结果位置。
4. **安排展示。** 优先给理由具体、证据充分的结果。贴合程度相近时，覆盖不同意象、叙述角度和歌手，再优先展示近期在这个需求下错过多次机会的歌。「换一批」沿用本次需求和证据标准，先从尚未展示的合格候选取。
5. **给用户原句和可执行动作。** 列表显示命中歌词、歌名、一句对应的理由，以及可用的试听入口。类比结果说明相似之处，片段结果标记范围。试听取主段内相邻的完整歌词句，远处的证据可以一起展示在解读里。每条结果都能回到确切的歌曲、歌词版本和行。

离线模型负责读完整歌曲，在线模型负责理解这一次的需求和核对少量候选。向量由本机的索引程序生成，首版可用 SQLite 管理档案、检索记录与版本，并在本机计算向量相似度。召回规模和精排预算以本机实测为准。

## 搜索记录与展示机会

| 记录 | 关键字段 | 用途 |
| --- | --- | --- |
| 搜索 | 搜索 ID、需求方向、查询时间、档案和排序版本 | 同一次刷新和换页沿用搜索 ID，允许追溯结果 |
| 召回与判定 | 歌曲 ID、解读 ID、召回路线、是否送审、贴合档位、原因 | 区分索引找不到、预算没送审、证据弱、明确冲突和合格 |
| 展示 | 搜索 ID、歌曲 ID、解读 ID、展示位置、实际进入可视区域的时间 | 计算近期展示量和合格却未展示的次数 |
| 试听 | 解读 ID、录音 ID、命中时间段、实际播放进度或失败原因 | 区分真的听到、主动跳过和取音源失败 |
| 明确反馈 | 需求方向、解读 ID、反馈类别 | 分别记录「这段说中了」「意思读错了」和「这次不想听这类」 |

同一次搜索中，一首歌在同一阶段只计一次，仍保留各路召回和各条解读明细。未送审的候选保持待判断。场景和需求方向分别记录。某首歌在「怀念过去，想被理解」里曝光多，可以在另一个适合它的需求下获得展示机会。

初版使用「上次展示以后，在同类需求下判为合格但未展示的次数」和上次展示时间做同档排序。全局展示量用于排查曲库覆盖。喜欢某首歌的记录由用户主动给出，试听和曝光事件各有单独含义。

## 场景歌单的新鲜感

场景使用稳定的 `scene_id`。用户可以把「放学回家」等说法归入同一个场景。每次回到这个场景听歌生成一个播放会话，暂停、刷新和续播沿用原会话。保存会话、场景、作品、录音和实际播放时间。音频有正式播放进度时计入该场景，预加载、只有展示、未播到和播放失败各自保留原有状态，试听另记。

1. **近期听过的作品先排除。** 自动歌单排除该场景最近五次有正式播放记录的历史会话中听过的作品。当天续播也要排除本次已经播过的作品。周一听过的作品，在随后五次放学路上都先避开。匹配和筛选以同一作品为单位，翻唱和现场版共用冷却记录。用户主动点播时可以重听。
2. **在检索阶段就应用排除。** 把已有作品组放进本次排除集合，各路召回给剩下的作品留够位置。队列生成后，自动补歌继续用同一规则，避免换一批又把已听作品送回来。其他场景近期听过的歌可在相近结果里靠后。
3. **给连续几天不同的表达。** 在符合当前需求的候选里，优先更换接连出现的歌手、意象和叙述角度。尽量维持当次用户要的歌词态度和用途。听过的作品即便另一段很贴切，也在同一冷却范围。
4. **曲库不足时缩短歌单。** 每次听满 5 首、固定排除前 5 次的话，要有 30 首合格作品才能持续填满 6 次。候选不足就给短歌单。用户愿意拓展时，可以接受「处境不同、感受相同」的结果，沿用同样的排除规则。

作品关系由程序用可信版本信息和人工校正维护。相同歌词可作为核对线索，作品关系未知时先按录音 ID 处理。具体录音的播放历史和时间轴保留给播放器。

## 落地顺序与验收

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| 样本档案 | 有证据的结构化档案和赏析 | 抽查意象、多语言、长歌词、反复副歌、立场转折和歌词缺失。核对原句、版本、段落与时间锚点 |
| 档案入库 | 全库增量导入、失败清单和检索索引 | 台账和源库数量对得上。中断可继续，重复导入和更新能定位到正确版本 |
| 单次搜索 | 语义召回、精排、按句试听与可读理由 | 用真实查询对照原歌词直搜、整篇赏析索引和结构化解读索引。评测查询独立于档案里的模型示例 |
| 常用场景 | 播放会话、近期去重、短歌单和角度轮换 | 同一场景连续运行 6 次，验证规定窗口内的作品零重复。覆盖翻唱、未播候选、续播、失败和冷却后重新入选 |

搜索评测分别看合格歌曲的召回、前五条贴合度、明确要求的冲突、推荐理由能否从原句核查，以及同类需求反复搜索时累计有多少合格作品露面。用「我想有人陪我舍不得」和「我想找一首帮我放下的歌」这类成对查询检查态度差异。上面的候选量和五次窗口是首版默认值，前者按速度和效果实测，后者按实际听歌频率与曲库大小调节。

## 后端运行

在仓库根目录运行这些命令。语义召回使用本机 Ollama 的 `qwen3-embedding:0.6b`。Ollama 服务未启动时，在另一个 PowerShell 窗口设置 `$env:OLLAMA_HOST = "127.0.0.1:11434"`，再运行 `ollama serve`。

```powershell
# 使用已建好的 15 首样本索引
py -3 -X utf8 kg_lyric_search.py --sample search "伤心"

# 按原句定位
py -3 -X utf8 kg_lyric_search.py --sample search "小黄花" --literal --limit 1

# 生成场景歌单
py -3 -X utf8 kg_lyric_search.py --sample search "今天想听有人陪我安静一会儿" --scene "放学路上" --session "after-school-01"

# 明确开启 DeepSeek 对本次查询的证据复核
py -3 -X utf8 kg_lyric_search.py --sample search "陪我舍不得，别劝我放下" --deepseek --review-limit 7

# 按档案导出进度更新正式索引，之后搜索时省略 --sample
py -3 -X utf8 kg_lyric_search.py index --full
```

`--deepseek` 从进程环境读取 `DEEPSEEK_API_KEY`。单次搜索常规上限为一次意图拆解和一次批量复核，后者最多 12 个作品。查询返回 `search_id`、证据行、片段时间、召回统计和模型用量。带硬限制的请求在复核不可用时可以浏览本地候选，自动场景歌单会避开这些尚待核实的候选。

- `next <search_id>` 从同次搜索取下一批。场景暂停或续播沿用同一个 `--session`，下次来到场景时换一个会话 ID。
- `event impression <song_id> --search-id <search_id> --event-id <event_id>` 记录结果实际可见。
- `event play <song_id> --search-id <search_id> --event-id <event_id> --played-ms 1500` 记录正式播放进度。场景和会话从该搜索继承。播放器也可直接传入 `--scene` 和 `--session` 记录主动点播。
- `event` 也支持 `preview`、`failed` 和 `feedback`。反馈用 `--detail fits`、`wrong_reading` 或 `not_today`。重传事件时沿用它的 ID。
- 自动作品合并使用相同的规范化标题和相同的歌词哈希。可在索引目录放置 `work-overrides.json`，把需要合并的各录音 ID 映射到同一个作品 ID，然后重建索引。

Python 调用入口是 `kg_lyric_search.LyricSearch`。正式索引和样本分目录保存，各有自己的索引和历史。运行 `py -3 -X utf8 -m unittest discover -s tests -p test_lyric_search.py` 可执行合成数据回归测试。
